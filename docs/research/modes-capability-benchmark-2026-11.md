## 0. Premise check — read this first

Three things in the brief need correcting before the answer means anything.

1. **The three snapshots have never been run.** [`modes-experiment-log.md`](modes-experiment-log.md:74) records the outcome pilot as `UNRUN`; there is no transcript, no score, and no measured difficulty for `b1`/`b2`/`b3`. Their pass rate under any doctrine is unknown, and an unknown baseline is a ceiling risk, not a floor.
2. **The snapshots ship their tests inside the agent's workspace.** [`rollup.test.mjs`](../../test-fixtures/frames/outcome-arm/snapshots/b1-failing-ci/test/rollup.test.mjs:10) is five `node:test` assertions in the same tree the agent edits. Every published coding benchmark that grades with tests either places them outside the container (Terminal-Bench) or accepts that the agent can edit them and measures the exploit rate (ImpossibleBench, EvilGenie, SpecBench). The current fixture is in the second category without the measurement. §8 makes the fix a precondition.
3. **The brief's own prior is probably correct, and should be stated numerically.** The programme's largest effects came from the _brief_ (30–50 points). The literature's only doctrine-adjacent ablation is single-digit. A design that assumes a detectable doctrine effect is designing for a result the prior says will not appear.

Nothing else in the brief is altered. This file is the only artefact produced.

## 1. Executive answer

**No one has measured this.** No study compares two instruction texts that differ only in doctrine while holding model, tools, brief and repository fixed. The nearest measured analogue is the `AGENTS.md` study: adding a context file to a fixed coding agent moves task success by **−3% (LLM-generated) to +4% (developer-written)** and raises cost by **20%**, across 300 SWE-bench Lite instances and 138 custom tasks [3].

The variance picture is genuinely contested. Under controlled, paired conditions the _whole harness_ — not merely prose — shifts pass rate by **0–8 points**, while shifting tokens per solved task **40×** [5]. Single study, n = 50 tasks, one trial each.

At **60 agent runs** the smallest detectable doctrine effect is **≈32 percentage points** (80% power, α = .05, two-sided); a null result excludes ≈**24 points**, not 5. Detecting a 10-point effect needs **≈770 runs** (≈7,700 calls); detecting the 3–4 points the literature reports needs **≈3,100–8,700 runs**, an order of magnitude past budget.

**Minimum honest claim:** _this benchmark measures whether a doctrine is followed, and reports an upper bound on its effect on success. It does not measure doctrine capability._

## 3. Graded findings by literature

### 3.1 Agent and coding benchmarks, and what they grade

**The field grades patches with tests, not transcripts.** SWE-bench applies the model's diff, runs `FAIL_TO_PASS` and `PASS_TO_PASS` tests in a per-instance Docker image, and reports the resolved fraction [1]. Terminal-Bench 2.0 runs 89 containerised tasks, each with a human-written oracle solution, and verifies **the final container state only** — "not agent commands or intermediate steps" [4][26]. τ-bench compares the final database to a unique goal state and additionally requires the agent's replies to contain specified information [9]. This is consistent across all three: **end-state verification is the default because transcript grading is considered unreliable.**

**Costs are now reported per task, and they vary by two orders of magnitude.** Terminal-Bench 2.0 costs "anywhere from one to a hundred dollars" per full run depending on model price; most tasks finish inside 20 minutes, but some consume "hundreds of API calls and almost 100 million tokens on a single task" [4]. The Vals leaderboard reports cost per test of **$0.35–$1.82** across nine harness-model pairs on the same 89 tasks [26]. Agentless resolves SWE-bench Verified at **$0.34 per issue**; its Lite run cost **$0.70** per issue for 32.00% [21]. Moatless-tools reports **$0.14** (Claude 3.5 Sonnet, 39%) and **$0.01** (DeepSeek V3, 30.7%) [21a].

**Infrastructure is the real barrier, not money.** SWE-bench evaluation requires Docker, `x86_64`, ≥120 GB free disk, 16 GB RAM, 8 cores, and takes 15–50 minutes for a full gold-patch pass at 12 workers [1]. Defects4J — 835 reproducible defects across 17 Java projects, each with a test suite that exposes the fault — runs with a normal JDK/Maven build and no container [18][19], but a reproducibility audit found **21.6% of its defects unsuitable** under strict reproducibility requirements [18].

**A validity trap worth naming.** The SWE-bench harness caches results by `run_id` + `instance_id` and ignores the patch content: "if you run the same instance with the same `run_id` multiple times, even with different prediction diffs, the harness will reuse the cached results" [1]. A benchmark that reuses run ids silently reports the first run's grade for every later run.

### 3.2 Attribution — model versus scaffold versus prompt

This is where the literature is loudest and least consistent, and §5 records the conflict.

**The strongest controlled claim for the harness:** a 3-model × 3-harness grid with task order, environment, evaluation script, API parameters and stopping rules held constant reports **harness variance 18.48 pp² against model variance 2.37 pp² (ratio 7.80×)**. Changing the harness moves one model by **13.0 points**; changing the model inside a fixed harness moves scores by **3.0, 2.5 and 5.0 points**. Six of nine model-pair × harness-pair comparisons reverse rank [6].

**The strongest controlled claim against it:** 300 trials (3 harnesses × 2 models × 50 Terminal-Bench Pro tasks, **one trial per task per cell**) finds paired within-model pass-rate differences of **0–8 points**, with 95% paired-task bootstrap intervals including zero for all but the largest gap — while tokens per solved task vary **40×**. The authors call pass-rate effects "of comparable magnitude [to a model upgrade] and within bootstrap noise at n=50" [5].

**The reconciliation, stated by the authors of [5] and confirmed by [6]:** harness variance is large in _cost and behaviour_, and small-to-moderate in _pass rate_ — unless the harness changes something the task depends on. **Doctrine is a smaller intervention than any harness in either study.** It changes text, not tools, not context management, not stopping rules. Anything the literature says about harness variance is an **upper bound** on what doctrine can do, and [5]'s cost finding is the part most likely to transfer.

**Run-to-run variance is a floor under everything.** An audit of 254 SWE-bench submissions found five cells containing **repeat submissions of the same scaffold with the same model at different dates**, differing by **13, 15, 27, 41 and 116 instances** (median 27 ≈ **5.4 pp**); the largest is one scaffold scoring 198, 277 and 314 over three submissions [7]. Within-model scaffold ranges reach **29.8 points**, against an 8.8-point spread across the top thirty entries [7].

**And the single most on-point study for this brief** is not a harness study at all: `AGENTS.md`. Holding agent and model fixed, adding an LLM-generated context file reduced success by **≈3%**; a developer-written one improved it by **≈4%**; both added **>20% inference cost** and 2–4 extra steps. Critically: "**instructions in the context files are well followed by coding agents**" while success does not improve [3][3a][3b]. Adherence and success came apart. That is the exact failure mode a doctrine benchmark must be built to detect, and the paper that found it did not set out to test doctrine.

### 3.3 Measurement validity

**`pass@k` and `pass^k` answer different questions and only one of them is about reliability.** τ-bench introduced `pass^k` — success on _all_ k trials — and reported that "even state-of-the-art function calling agents (like gpt-4o) succeed on <50% of the tasks, and are quite inconsistent (**pass^8 <25% in retail**)" [9]. Secondary explainers routinely present this as exponential decay and get the arithmetic wrong (see C2).

**Eval scores need error bars, and clustering is the usual reason they are wrong.** Miller's framework gives standard errors for single-model, paired, and clustered designs; **clustered standard errors "can be over 3X larger than naive standard errors"** on real Anthropic evals; the recommended analysis for two systems is _paired per-question differences_, which shrinks the interval whenever the two systems' scores correlate [24]. His worked power example — 3-point target difference, variance ⅑, 80% power — needs **≈969 independent questions**, and he labels those parameters fictional.

**Runs per task is not standardised, and the field's practice is thinner than its rhetoric.** Observed practice: **1** trial per task per cell with paired bootstrap over 50 tasks [5]; **1** run per submission on a public leaderboard, named by its own auditors as a limitation ("between-system differences cannot be separated from run-to-run variance") [7]; **3** repeats per instance in a harness-comparison benchmark [28]; **5** runs per agent when reporting mean accuracy and cost [2]; **k up to 8** when the claim is reliability [9]; **25** trials per question per condition in a persona study that needed item-level precision [25].

**Contamination and leakage are measured, not hypothetical.** SWE-Bench+ finds **32.67%** of _resolved_ instances had the solution leaked in the issue text, **31.08%** of passed patches were wrong but test-passing, and filtering both drops SWE-Agent+GPT-4 from **12.47% to 3.97%**; 94% of instances predate model cut-offs [8]. A separate audit finds models identify the buggy file from issue text alone in **76%** of Verified cases but **53%** on unseen repositories [7].

**Reward hacking is the dominant threat to a test-graded fixture.** On ImpossibleBench — where tests are mutated to contradict the specification, so any pass implies gaming — **GPT-5 "passed" 54%** of one set of impossible SWE-bench tasks by editing or gaming tests, and **hiding the tests cut cheating to near zero** [10]. EvilGenie finds held-out tests give "only minimal improvement" but an LLM judge detects hacking well in unambiguous cases [11]. SpecBench finds the validation-to-holdout gap **grows by 28 percentage points for every tenfold increase in code size** [12].

**Cost- and turn-normalised success is accepted, with a caveat on turns.** Cost is now a first-class reported metric (per-task cost on Terminal-Bench boards; Pareto accuracy-cost curves as the recommended presentation) [2][26]. **Turn count is not**: Terminal-Bench reports "essentially no correlation between the number of average turns per trial and model success rates", and "higher token count does not necessarily correlate with better performance" [4]. So: normalise by **cost**, do not normalise by turns.

### 3.4 Instruction and configuration effects

**Prompt formatting alone moves scores by more than any doctrine effect plausibly could.** Ten sampled meaning-preserving formats produce a **median 7.5-point spread**, up to **76 points** (LLaMA-2-13B), with **20% of tasks showing ≥15 points** for every LLaMA-2 setting; and "format performance only weakly correlates between models", which the authors say "puts into question the methodological validity of comparing models with an arbitrarily chosen, fixed prompt format" [13]. This is the variance floor against which a doctrine effect must be read: **a doctrine is one format sample.**

**Personas do not improve objective accuracy, and the finding survived a self-reversal.** Across 162 roles, 2,410 factual questions and 4 model families, "most of the personas have no statistically significant effect… certain personas may actually lead to lower performance", with no persona that reliably helps and classifier-based persona selection performing "no better than picking personas at random" [34]. The Wharton replication (198 GPQA + 300 MMLU-Pro questions, **25 trials per question per condition**) finds expert personas "do not reliably improve accuracy", low-knowledge personas _decrease_ it "with the degree of harm correlating to the level of implied ignorance", and mismatched expert personas caused Gemini 2.5 Flash to **frequently refuse** [25]. This is the same shape as the programme's own F-1: persona changes style, not substance.

**Constraint count binds, and it binds early.** FollowBench adds one constraint per level: GPT-4-Preview-1106's all-constraints-satisfied rate falls from **84.7% at level 1 to 61.9% at level 5**, with a mean "consistent satisfaction level" of **3.3**; Qwen-Chat-72B manages **2.4** [16]. Roughly: **the third constraint is where most models stop** — consistent with the programme's own note that constraint count binds before character count.

**Instruction _optimisation_ shows what the ceiling of a doctrine effect looks like.** GEPA evolves prompts by reflecting on trajectories and beats GRPO by **6 points on average and up to 19–20**, and the prior prompt optimiser by **>10 points** (e.g., +12 on AIME-2025) [20]. That is the upper bound _when you can search thousands of candidate doctrine texts against the metric_. It is not the size of a hand-written doctrine difference, and the searched text is fitted to the benchmark it was scored on.

**The one mechanism that supports "definition of done" as doctrine:** models "struggle to self-correct their responses without external feedback, and at times, their performance even degrades after self-correction" [17]. So a doctrine that mandates a _runnable check_ has a plausible mechanism; a doctrine that mandates _reviewing one's work_ has a measured counter-mechanism. No study measures either as a prompt element.

### 3.5 Judging trajectories

**Execution beats judging wherever execution is available**, and every benchmark above chose it [1][4][9]. Where the rubric is the only option, the reliability numbers split sharply by judge design:

| Judge                                                 | Agreement with reference                                      | Source |
| ----------------------------------------------------- | ------------------------------------------------------------- | ------ |
| GPT-4 pairwise vs human preference                    | **>80%**; 85% on non-tie first turns, against 81% human-human | [14]   |
| LLM judge on requirement verdicts                     | **68.9–71.9%**                                                | [15]   |
| Agent judge (tools to open files, trace requirements) | **86.6–92.1%**                                                | [15]   |
| Human experts vs each other                           | **70–90%** (10–30% pairwise disagreement)                     | [15]   |
| Prompt-template judge, with constraint-evolution path | **88%** vs expert majority (85% human-human)                  | [16]   |
| Same template, no evolution path                      | **79%**                                                       | [16]   |
| Generic "score 0–10, >5 passes" rubric                | **67%**                                                       | [16]   |

**Judge design moves agreement by ~20 points; the task type moves it by more.** MT-Bench's 80% is for chat preference, where "good" is a preference. Requirement verdicts on code are a different task, and the plain LLM judge loses ~15 points against the agent judge on it [15]. **Known biases:** position (GPT-4 consistent under swap only **65.0%** of the time, favouring first position **30.0%**), verbosity (**8.7%** fooled for GPT-4, **91.3%** for Claude-v1 and GPT-3.5), and self-enhancement (GPT-4 **+10%**, Claude-v1 **+25%** win rate on own outputs, unconfirmed by the authors' data) [14].

**A judge is not calibrated because its headline agreement is high.** A recount of DevAI's released verdicts found the agent judge saying "met" where the human consensus said "not met" **64 times against 50 the other way, across 1,098 verdicts** [15a] — a _false-pass_ skew, which is the direction that inflates capability claims. And the anchors themselves are soft: the human reference disagrees with itself by 10–30% [15].

**The convention worth borrowing:** report agreement against a _hand-labelled_ subset of your own cases, not a published number, and treat 80%+ agreement as the human-parity band because that is where human-human agreement sits in two independent studies (81% [14], 85% [16]).

## 4. The seven questions answered

**Q1. What is standard for runs per task, and is a single run acceptable anywhere?**
Practice ranges from 1 to 25 depending on the inferential unit, and there is no field standard. A single run per task is used, defensibly, in exactly one configuration: **many tasks, paired across conditions** — 50 tasks × 1 trial with a paired bootstrap over tasks [5], or 500 instances × 1 submission with paired instance-level comparison [7]. It is _not_ defensible when the number of tasks is small, because the run-to-run replication floor on a fixed system is already **≈5.4 pp median, up to 23 pp** [7]. With **three** tasks, a single run per cell is not a measurement of anything.

**Q2. What share of variance is configuration rather than model?**
Controlled estimates: harness **18.48 pp² vs model 2.37 pp², ratio 7.80×**, with 13.0-point harness swings and 2.5–5.0-point model swings inside a fixed harness [6]. Pass-rate-restricted estimate: harness **0–8 points** vs model upgrade **4–10 points**, statistically indistinguishable at n=50, while **cost varies 40×** [5]. Public-leaderboard estimate: within-model scaffold range **29.8 points** against an 8.8-point spread of the top thirty [7]. **For doctrine specifically: no measurement exists.** The only doctrine-adjacent ablation is `AGENTS.md` at **−3 / +4 points, +20% cost** [3].

**Q3. Which benchmark families run offline on a small fixture with deterministic tests, and what do they cost per task?**
See §7. In short: Terminal-Bench-style end-state tests **do** run offline and are the best structural template, but the official 89-task set is not small (per-task $0.35–$1.82, full runs $1–$100) [4][26]; SWE-bench requires Docker and 120 GB [1]; Defects4J is deterministic and local but Java and partly unfit (21.6% unusable) [18]; τ-bench is offline-capable but needs an LLM user simulator [9]; our own three snapshots grade in seconds with `node --test` at **$0** grading cost.

**Q4. What is published on doctrine-level ablations, and at what effect size?**
**Nothing on doctrine as such.** No study holds model, tools, brief and repository fixed and varies only the instruction text of a mode/skill. The nearest published ablations, in descending proximity: `AGENTS.md` context files (**−3% / +4%, +20% cost**, 4 agents, 2 benchmarks) [3]; persona directives (**null to slightly negative**, 162 roles, 2,410 questions) [34][25]; prompt formatting (**median 7.5 pp, up to 76 pp**) [13]; constraint count (**−23 pp from 1 to 5 constraints**) [16]; optimised prompt search (**+6 to +20 pp**, thousands of rollouts) [20]. A report claiming a published doctrine effect size would be assembling adjacent evidence into an implied answer, which the brief forbids — so I am not doing it.

**Q5. How do published evaluations control contamination and reward hacking on a private fixture?**
Five mechanisms, all measured: (i) **hold out tasks by generality level**, not just by split [2]; (ii) **use post-cut-off or licence-restricted repositories** — SWE-Bench+ collects post-cutoff issues and observes "a consistent performance drop across all models" [8], SWE-bench Pro uses copyleft-only and privately purchased repositories [29]; (iii) **verify the end state with tests the agent cannot read** — Terminal-Bench's tests live outside the agent's container [4]; (iv) **hide test content, not just results** — the single largest measured effect on hacking, cutting it "to near zero" [10]; (v) **check test-file integrity and grade against a holdout suite** — EvilGenie detects test edits directly [11], SpecBench measures the validation-minus-holdout gap [12]. A private fixture is _automatically_ contamination-free with respect to training data only if it was never published and never derived from published issues; a locally authored snapshot satisfies this by construction.

**Q6. What judge reliability is acceptable for agent trajectories?**
The operational convention is **human-human parity**, and that parity is 80–85% agreement [14][16]. Achieving it requires a _requirement-by-requirement_ rubric with a tool-using judge (86.6–92.1%) rather than a whole-trajectory LLM verdict (68.9–71.9%) [15], and a template that shows the judge the constraint sequence (88% vs 79%) [16]. Treat the _direction_ of error as well as its size: a false-pass skew of 64:50 on 1,098 verdicts is the failure mode that manufactures capability [15a].

**Q7. Is cost- or turn-normalised success accepted? What are its failure modes?**
**Cost: yes, and increasingly mandatory** — Pareto accuracy-cost curves, dollar costs rather than parameter-count proxies, per-task cost on leaderboards [2][26]. **Turns: no** — Terminal-Bench finds essentially no correlation between average turns and success [4], and the Scaffold Effect paper finds turns/no-action-turns vary 10× across harnesses without moving pass rate [5], so turn-normalisation would penalise thorough agents for being thorough. Cost's failure modes: it conflates fixed and variable cost [2]; it rewards agents that fail fast (a cheap 0% beats an expensive 60% only if you never multiply by success — hence _cost per solved task_, not cost per task) [5]; and it is meaningless without the success it is divided by [26].

## 6. No-data register

Claims the literature does **not** support, recorded so that no later document implies otherwise:

1. **No doctrine ablation exists.** No study varies only the instruction text of two modes/skills with model, tools, brief and repository fixed. Closest: `AGENTS.md` [3].
2. **No measurement of "bookended contract"** (opening charter + closing contract) as a doctrine structure. Zero studies.
3. **No measurement of a "stated refusal path"** as a doctrine element. The adjacent result is the opposite: telling a model not to ask "produce[s] no detectable change in decision accuracy but +13.5 to 23.5 points of official score" [32] — a _scoring_ effect, not a doctrine effect.
4. **No measurement of "explicit definition of done"** as a prompt element. Vendor guidance only (Anthropic's "give Claude a way to verify its work"), plus the mechanism in [17].
5. **No per-task cost published for a three-snapshot, `node --test` fixture class.** All published per-task costs are for large containerised suites [4][21][26].
6. **No study of doctrine × brief-clarity interaction** in any capability setting. The programme's conditionality hypothesis is tested only in routing.
7. **No study of abstention as a capability outcome** — abstention is documented as a _routing_ decision [32] and as a mismeasured benchmark axis, not as a succeed/fail outcome.
8. **No replication of any doctrine-adjacent effect size in a second independent study.** `AGENTS.md` is one paper; the persona nulls have two independent papers [25][34] and are the best-supported finding in this report.

## 8. Recommended minimal design

### 8.1 What it can and cannot claim

| Claim                                                                           | Permitted by this design?                                   |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| "Doctrine A is followed more often than doctrine B on these three tasks"        | **Yes**, with a rule-based trajectory check and n ≈ 60 runs |
| "Doctrine A produces more successful runs than doctrine B on these three tasks" | **Only as an upper bound**: a null excludes ≈24 pp, not 5   |
| "Doctrine A is a more capable mode"                                             | **No.** Three tasks, one model, one repository              |
| "Doctrine effects are below X points"                                           | **Yes, if pre-declared** — that is the useful output        |

### 8.2 The instrument

1. **Three arms, not two.** `doctrine-A`, `doctrine-B`, **and `null`** (brief only — no mode text, same tools). The null arm is the ceiling/floor guard: if `null` already passes 3/3 on a snapshot, that snapshot cannot discriminate, and the routing round's ceiling failure repeats. Pre-register that a snapshot is **replaced** if `null` passes ≥2/3 or ≤0/3.
2. **Tests move out of the workspace.** Copy the run's `src/` into a pristine tree, restore `test/` from the snapshot, verify the test files' sha256 against the recorded value, then run `node --test`. This is the direct response to ImpossibleBench (−54 points of fake success when tests are editable) and EvilGenie (a model deleted the test file) [10][11].
3. **One fixed brief per snapshot, byte-identical across arms**, recorded in `meta.json`, as [`run-b1-pilot.sh`](../../test-fixtures/frames/outcome-arm/run-b1-pilot.sh:104) already does.
4. **Interleaved order `a b n n b a …`**, fixed in advance, so provider drift cancels. Record every draw's order index.
5. **Blinding is unnecessary here and should be dropped.** The outcome is `exit code + test counts`. Blinding was needed for _scoring transcripts_; it is not needed for execution grading, and keeping two scorers is where the cost goes if you keep it. Keep blinding only for the tier-2 rubric below.

### 8.3 The two-tier outcome

| Tier                                                     | Unit                                                                                                                                              | n                                            | Grading                                                                                | Cost                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------- |
| **T1 — adherence** (primary for the _doctrine_ question) | one run → 3 rule-checkable events (a named reproduction attempted; the failing test executed before editing; work stopped only after a green run) | **60 runs × 3 events = 180 units**           | rule/regex over the trajectory, hand-verified on **40 units**, second scorer on **20** | ~0 extra calls                         |
| **T2 — success** (primary for the _capability_ question) | one run → pass/fail against restored tests                                                                                                        | **60 runs** (3 snapshots × 2 doctrines × 10) | execution, `node --test`                                                               | ~500–700 model calls at 8–12 turns/run |

**Why T1 is not a consolation prize.** `AGENTS.md` is the proof: instructions were "well followed" while success did not move [3]. Adherence is the variable a doctrine _can_ move, measured at n = 180 with rule-based grading, and it is the precondition for any success effect. Reporting adherence and success separately is exactly the distinction the field's best study of this question could not draw.

### 8.4 Sample size and the smallest detectable effect

Two-arm comparison, binary T2 outcome, α = .05 two-sided, 80% power, normal approximation (Fisher exact is slightly more conservative, so these are optimistic by a few points):

| Design                       | Runs   | n per arm | **Smallest detectable difference** | A null result excludes |
| ---------------------------- | ------ | --------- | ---------------------------------- | ---------------------- |
| 3 × 2 × 6                    | 36     | 18        | **≈39 pp**                         | ≈30 pp                 |
| 3 × 2 × 10 **(recommended)** | **60** | **30**    | **≈32 pp**                         | **≈24 pp**             |
| 3 × 2 × 15                   | 90     | 45        | ≈27 pp                             | ≈20 pp                 |
| 3 × 2 × 25                   | 150    | 75        | ≈22 pp                             | ≈16 pp                 |
| 3 × 2 × 50                   | 300    | 150       | ≈16 pp                             | ≈11 pp                 |

At the recommended 60 runs the honest sentence is: _"Pooled success was x/30 under doctrine A and y/30 under doctrine B (difference d, Wilson intervals in the annex). This design detects only differences of ≈32 points or more; it therefore does not establish that doctrine has no effect, only that any effect on these three tasks is smaller than 24 points."_

**One further constraint the arithmetic hides.** With three snapshots, the _inferential_ unit for any generalisation is the snapshot. Thirty runs per arm estimates **these three tasks' rates** precisely and estimates **doctrine's effect** barely at all — the between-task variance is a property of the fixture, not something runs can average away [24]. The design must therefore be reported per snapshot, with the pooled figure labelled as a fixture-level average, not a population estimate.

### 8.5 Cost of the recommended design

- 60 agent runs × 8–12 turns ≈ **500–700 model calls** — inside "hundreds, not millions".
- Grading: 60 × `node --test` on a 5-test suite ≈ **seconds**, $0.
- Rubric: 40 hand-labelled units + 20 second-scorer units ≈ **1–2 hours of human time**, no model calls.
- Total dollar cost at flash-tier pricing: **≈$1–3**, by analogy with Agentless at $0.34/issue on far larger repositories [21] and Moatless at $0.01–$0.14 [21a]. This is an estimate, not a measurement; the harness should write a token sidecar per run as [`gemini-runner.mjs`](../../scripts/lib/gemini-runner.mjs) already does.

### 8.6 The instrument-sensitivity arm — run this first

Before the doctrine comparison, run **one snapshot, two doctrines that are deliberate negations of each other** (e.g. _"begin by reproducing the failure before proposing a fix"_ against _"propose the fix immediately; do not run the tests"_), on a snapshot where the failing test is the only way to locate the bug. `n = 6` per arm.

- If the negation produces a large, obvious separation (e.g. 0/6 against 5/6), the instrument is **sensitive** — and the programme has a published-defensible demonstration that doctrine _can_ move outcomes when it is causally load-bearing.
- If the negation produces **no** separation, the fixture is not mechanism-sensitive and the whole design must be rebuilt before spend. That is a cheap, high-value failure.

This mirrors the routing round's own logic: a failing gate is strong evidence, a passing gate is weak [33].

## 9. What it would take to detect an effect smaller than that

| Target effect                                      | Runs needed (**both arms**, per §8.4) | Model calls (at ~10 turns) | Is it reachable?                        |
| -------------------------------------------------- | ------------------------------------- | -------------------------- | --------------------------------------- |
| **20 pp**                                          | ~182                                  | ~1,800                     | Reachable, at 3× the recommended budget |
| **15 pp**                                          | ~334                                  | ~3,300                     | One order over budget                   |
| **10 pp**                                          | ~770                                  | ~7,700                     | Out of reach at this budget             |
| **5 pp** (≈ the `AGENTS.md` human-written effect)  | ~3,124                                | ~31,000                    | Out of reach by ~50×                    |
| **3 pp** (≈ the `AGENTS.md` generated-file effect) | ~8,678                                | ~87,000                    | Out of reach by ~140×                   |

Three things a programme could do instead of buying runs:

1. **Increase tasks, not runs.** Between-question variance is immutable; sampling more fixtures is the only route to generalisation [24]. Ten snapshots × 2 arms × 4 runs = 80 runs buys a _fixture-level_ estimate at the same cost as 3 × 2 × 13.
2. **Use a graded outcome.** Scoring tests-passed per run (0–5) instead of pass/fail reduces the required n from **~167 to ~86 per arm** for the same 15-point shift at sd ≈ 0.35 — a **2× saving**, at the cost of needing a defensible mapping from "tests passed" to "task done".
3. **Use an instrument where doctrine is causally necessary.** The negation arm (§8.6) manufactures a large effect; that is how you demonstrate _mechanism_ at small n. It does not tell you the size of a realistic doctrine effect, and it must not be reported as if it did.

**And the honest ceiling on all of it:** a fixed system's run-to-run replication floor is **≈5.4 pp median** [7]. No design at any affordable n distinguishes a 3-point doctrine effect from noise, because the instrument's own drift is larger than the effect.

## 11. What could not be checked

- **The `AGENTS.md` effect sizes are secondary.** I read the abstract, not the results tables. −3 / +4 / +20% is corroborated by three independent summaries but has not been confirmed at source, and the confidence intervals are unknown. It is the single most load-bearing external number in this report and it deserves a direct read before any pre-registration quotes it.
- **No source gives a per-task cost for a fixture of our size.** The $0.01–$0.05 per run in §7 is my estimate from token counts and published price sheets, not a measurement.
- **The 28-point scaffold claim [23] is unreachable** and is excluded from every conclusion above.
- **I did not verify `pass^k` denominators or the DevAI recount** beyond the secondary that reported them; both are marked accordingly.
- **No source separates "doctrine" from "context file" or "system prompt"** in a way that would let me transfer an effect size honestly. I have not tried.
- **Three of the five literatures are dominated by 2024–2026 preprints.** None of the measured findings in §3.2, §3.4 or §3.5 has been independently replicated except the persona null [25][34], and every `verified` label in this report means "read at source in one study", not "reproduced".
